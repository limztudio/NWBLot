# Offline font assets and compact SDF atlases

Status: implemented on `main`. The UI text service shapes with the original SFNT bytes and optionally paints from a matching signed-distance atlas. The offline builder prepares those two payloads before normal asset cooking. Toolkit work is tracked in [the custom UI plan](custom_ui_plan.md).

## Authoring contract

`utilities/font_builder` accepts a static `.ttf` or `.otf` face, or an existing prepared `.font`, and publishes exactly two same-stem files:

| File | Content |
| --- | --- |
| `<stem>.nwb` | Independent `font face;` and `font_atlas atlas;` declarations with readable bake settings, editable vertical layout metrics and every glyph mapping. `atlas.font = face;` selects the typed source, and `asset_bunch bunch = [face, atlas];` exports both assets. No authored schema-version or hash fields are required or accepted. |
| `<stem>.font` | Binary FON2 version 1 source containing the exact admitted SFNT and compact linear R8/RG8/RGB8/RGBA8 images. Internal lengths and SHA-256 values protect the source and pixels. The original TTF/OTF does not need to remain in the asset tree. |

The asset builder scans ordinary `.nwb` declarations. Independent font and atlas importers derive the same adjacent `.font` path from the original metadata basename, including when asset-bunch items have their own published identities. The bunch publishes `<metadata virtual path>/face` and `<metadata virtual path>/atlas`, and resolves the local `atlas.font = face` relation. For example, the Latin defaults publish `engine/ui/fonts/default/latin/face` and `engine/ui/fonts/default/latin/atlas`. The font importer reads SFNT bytes without allocating image payloads. The atlas importer admits readable mappings/settings, derives face facts from SFNT and image layouts from the FON2 directory, validates pixel integrity, and copies original positioning-table bytes from the source. It then binds the declared typed font identity and applies the shared atlas validator. Missing, mismatched or malformed pairs fail admission. Cook time reconstructs runtime assets without rerasterizing the face.

Standalone `font` and `font_atlas` declarations are also supported through the same importers, with an explicit typed font reference for the atlas and a same-stem FON2 source. The retired `font_bundle` declaration, separate atlas companions, hash-named payload sidecars and zstd/base64 text embedding are unsupported. Regenerate old assets from their original fonts; source and runtime readers retain only their current formats.

The `font face;` declaration has no authored fields. The atlas requires its typed `font` reference, `bake_ppem`, `spread_pixels`, `raster_mode`, editable `ascender_units`/`descender_units`/`line_gap_units`, and `glyphs`. Cooking derives face index, units per em, glyph count, and image dimensions/channels from the paired source; the guard is fixed at one texel. Metadata rejects those copied facts and a `groups` list.

Every source glyph has one record in source order. Empty glyphs contain exactly `{ "advance_units": number }`, with the advance required. Bitmap glyphs contain exactly `group`, `channel`, `x`, `y`, positive `width` and `height`, `plane_left`, `plane_top`, and `advance_units`. The cooker derives glyph ID from list ordinal, drawable state from the presence of `width`, and right/bottom from left/top plus width/height multiplied by `units_per_em / bake_ppem`. Empty geometry is zero internally. Metadata rejects authored `id`, `drawable`, `plane_right`, `plane_bottom`, and fixed-zero empty geometry. Nine significant digits and explicit floating-point syntax preserve the exact f32 metric bits through the readable document.

The current runtime codecs are FON1 version 1 for `Font` and FTA1 version 2 for `FontAtlas`. The FTA1 reader rejects version 1. A prepared `.font` stores the same SFNT bytes used by FreeType and HarfBuzz, so later atlas regeneration and native-coverage fallback do not require the original external file. The original font notices remain next to the defaults; see the [default-font README](../impl/assets/ui/fonts/default/README.md).

## Builder and publication

Build the utility with `python -m launcher build nwb_font_builder`, or build and run it with `python -m launcher font-builder`; see the [utility README](../utilities/font_builder/README.md) for executable examples. The utility admits a readable static SFNT face of at most 32 MiB, using face index zero, and retains every source glyph ID, including glyph zero and nondrawable whitespace. It refuses unsupported fonts, truncation, invalid bake options, and capacity exhaustion rather than silently dropping glyphs or changing settings.

The pinned FreeType 2.14.3 SDF sources come from vendor revision `0a0221a1347e2f1e07c395263540026e9a0aa7c7`. `--renderer bitmap` is the default: it renders unhinted grayscale coverage and then a bitmap SDF. `--renderer outline` requests direct outline SDF and fails if the face cannot support that path. Utility defaults are 64 pixels per em, spread 8, a maximum square packing extent of 1024 pixels, and at most eight groups. `--extent` accepts non-power-of-two values from 32 through 2048. Shared bounds are 65,535 glyphs, at most 2048 pixels on each image axis, one through four stored channels per group, 128 MiB of image bytes and 32 MiB of positioning tables, ppem 16..256, and spread 2..32. Staging remains bounded by the maximum four-plane packing capacity.

Packing sorts glyphs by descending bitmap height, descending width, then ascending ID. It traverses guarded shelves in R/G/B/A page order, without glyph rotation. Each group is then cropped to the union of drawable glyph rectangles plus their exterior guards, and stores channels through its last occupied plane. Compaction preserves every retained SDF and guard value without resampling. The builder validates the complete candidate, stages and flushes both outputs, verifies their bytes, then publishes `.font` followed by `.nwb`. Replacement of an existing complete pair requires `--overwrite`; a partial pair or occupied work path fails. Failed rasterization, validation, staging, or replacement preserves the previous output. Repeating a bake from identical SFNT bytes and settings on one platform produces byte-identical output. Native Linux execution is still needed to qualify cross-platform byte equality.

## Atlas format and rendering

Each logical scalar page initially maps to one packing channel: page `p` uses group `p / 4` and channel `p % 4`. Compaction retains that group/channel mapping and removes only unused trailing planes. Alpha, when stored, is a fourth distance plane. Width and height are independent, with no square or power-of-two requirement. Rows are top to bottom with tightly interleaved one-, two-, three- or four-channel bytes and no padding or mips. Every exterior guard contains zero. The UI uploader chooses linear `R8_UNORM`, `RG8_UNORM`, `RGB8_UNORM` or `RGBA8_UNORM` for bilinear clamp sampling. If RGB8 sampling is unsupported, it expands that group once to RGBA8 for upload while preserving all three distance planes. Source pixels receive no sRGB conversion, premultiplication, image mip generation or lossy compression.

FON2 version 1 stores a 56-byte little-endian header containing magic, version, face index, SFNT byte count, image group count, zero reserved flags and an internal SFNT SHA-256. Each 48-byte directory entry declares width, height, channel count, byte count and pixel SHA-256. The directory is followed by exact SFNT bytes, then each tightly interleaved image. Pixel length is exactly `width * height * channelCount`; the complete layout consumes the file. Glyph mappings, bake settings, and editable vertical layout metrics are authored in `.nwb`; face facts and image directory values stay in the prepared source.

After cooking, runtime FTA1 version 2 stores a fixed 164-byte little-endian header, 52-byte records for all glyph IDs, 48-byte group headers followed by exact pixels, and 40-byte positioning-table headers followed by exact table bytes. Group and table hashes are internal binary fields. Bounded counts and lengths are checked before allocation; reserved fields must be zero. The shared validator checks guarded same-channel rectangle overlap and geometry bounds. Invalid reads preserve previously loaded assets.

Drawable records hold group/channel, pixel rectangle, baseline-relative plane bounds in design units, and an inspection advance. Plane bounds include the SDF spread; the guard texel lies outside the sampled rectangle. Shape and placement still come from HarfBuzz's selected face, glyph ID, cluster, advance, and offset. Atlas advances and positioning exports are never applied again after shaping.

The atlas carries the original `kern`, `GPOS`, and `GDEF` table bytes with hashes. That preserves legacy pairs, class matrices, script/language/feature selection, lookup order, contextual structures, and device data without expanding all glyph pairs. The admission validator checks bounded roots and supported pair/class structures; other positioning families retain their original bytes after bounded root checks. It is not a general OpenType sanitizer.

In the fixed internal FreeType scalar SDF encoding, byte 128 represents zero distance and positive distance is inside the glyph. The shader chooses one channel and reconstructs `(sample * 255 - 128) * spread / 128`, using derivatives to adjust coverage. The qualified SDF interval is **0.75..1.5 times the bake ppem** in physical pixels; outside it, the same selected face uses native grayscale coverage. The default 32-ppem Latin and Korean atlases therefore serve 24..48 physical pixels per em. Below that interval, native coverage preserves the antialiased bottom row of small descenders. Recorded qualification compared Latin `A`/`o`/`e`/`g`/`q` and Korean `한` at 48 glyph/scale combinations within this interval, requiring at most one pixel of edge displacement and mean coverage error no greater than 0.04. The former quality unit target is retired; these figures remain the historical qualification for the shipped atlases. Larger magnification failed at sharp corners, so this distance representation does not promise unlimited zoom.

Installed font versions copy SFNT bytes and immutable compact atlas image records. Existing layouts and paint snapshots retain their versions across asset release, font replacement, and display-scale changes. The GPU path uploads each group in its selected linear format, selects a single channel per glyph draw, imports readiness into the frame graph, and retains resources through the final compositor consumer. The independently prepared UI layer and premultiplied SDR/HDR composition retain their existing behavior.

The shipped faces bake at 32 ppem with spread 8. Latin stores 1024 × 1024 RGBA8 and 1024 × 1023 RG8 groups, totaling 6,289,408 image bytes (5.998046875 MiB). Korean stores two 2048 × 2048 RGBA8 groups, one 2048 × 2047 RGBA8 group and one 2048 × 1209 R8 group, totaling 52,799,488 bytes (50.353515625 MiB). Combined image data is 56.3515625 MiB, a reduction of 15.6484375 MiB (21.733941%) from the previous 72 MiB. Actual GPU allocations can include alignment and tiling overhead; the defaults contain no three-channel group requiring the RGB8 upload expansion.

### Historical UASTC trial

Before channel and rectangle compaction, the conditional UASTC preference was tested against the then-shipped four-channel atlases. The pinned LDR `tex_conv --linear` encoder compressed block-aligned 96x96 crops from the actual RGBA pages; the pinned Basis decoder reconstructed their first mip. A probe selected each glyph's assigned channel and compared bilinear SDF coverage with the lossless page at 24, 32, and 48 physical pixels per em. The sample included Latin `A`, `o`, `e`, `i`, `m`, `g`, `q` and Korean `한`, `가`.

The compressed `g` and `q` edges moved up to **2 pixels** at 48 pixels per em; `A` and `한` also reached 2 pixels. At the stored distance threshold, `g` changed sign in 43 of 1,344 glyph texels and `한` in 69 of 1,980. The largest additional mean coverage error against the lossless page was 0.0306 (`한` at 32 pixels per em). This representative comparison did not repeat the native-outline qualification, but it already exceeds the current one-pixel edge budget relative to the lossless atlas. The format therefore retains exact SDF bytes. At that time, directly sampled UASTC could have reduced the raw 8 MiB Latin and 64 MiB Korean payloads to 2 and 16 MiB; those figures describe the previous four-channel layout. A compression strategy for the current compact groups needs its own native-outline quality gate before changing the format.

## Verification

The output integration suite exercises complete Latin and Korean generation, FON2 source decoding, bunch expansion and both metadata importers, reconstructed runtime FTA1 version 2 decoding, all-glyph coverage and exact f32 metric bits, compact group bounds and guards, non-power-of-two capacity, exact source positioning bytes, deterministic repetition, raw-SFNT and prepared-font equivalence, overwrite refusal, failed-capacity preservation, partial-pair/work-path refusal, corrupt binary/mapping rejection and relocation of the two files. Packing regressions cover all four channel counts and exact guarded bytes. The independent metadata importer tests cover standalone and bunch publication, readable metadata mismatches, missing/mismatched pairs and rejected retired formats. The recorded supersampled-outline comparison established the scale qualification above; its former unit target is no longer part of the current suites. UI smoke and Testbed exercise the cooked default pair through the normal asset pipeline.

Windows ARM64 builds and tests can run on the current host. Changed Linux code can be checked with the Linux x86_64 syntax harness, but that does not establish native Linux linking, cross-platform bake byte equality, or compositor behavior. Live HDR presentation and other fonts' visual quality remain separate qualification work.
